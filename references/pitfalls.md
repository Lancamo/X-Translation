# pitfalls.md — 踩坑全记录（含实测数据）

## 一、会让管线直接崩的

### 1. 字号试算用 `insert_htmlbox` → 被 OOM Killer 杀掉

**症状**：全量跑到一半进程消失，`echo $?` = 137。

**真因**：`insert_htmlbox` 每次调用都往目标文档里嵌一份字体。逐条二分试算 = 每条嵌 8~10 次，
1,277 条就是上万份字体对象常驻内存。

**处理**：改成**纯算术估字号**（`fit_size_arith`）——按字符宽度估行数、二分搜索，
偏差交给插入时的 `scale_low` 兜底。临时试算页如果非要保留，**每次重建**，
否则同一页反复插入会让内容无限膨胀（几十条看不出，全量必卡死）。

### 2. 成品体积暴涨到 GB

**真因**：`insert_htmlbox` 每页各嵌一份完整 CJK 字体（思源宋体单字重 ~14 MB）。

**处理**：`doc.subset_fonts()` 必须在保存前调用：
`doc.save(out, garbage=4, clean=True, deflate=True, deflate_fonts=True)`。
实测 90 页最终 38.2 MB。

### 3. 保存时把文件写坏 / 丢失

**真因**：后台任务正在写输出文件时，删掉了那个文件。进程句柄指向已 unlink 的 inode，
写完的字节再也找不到。

**处理**：**绝不在后台任务运行时删它的输出文件**。要换输出名，就改脚本参数再跑。

### 4. `import` 位置错导致 `NameError: Path`

复制/改写脚本时把 `BASE = Path(...)` 插到了 `from pathlib import Path` 之前。
打包脚本里加了 `ensure_path_import()` 兜底：用了 `Path(` 却没 import 就自动补。

## 二、分类器/判据类（假阳性与假阴性）

### 5. OCR 把中文误读成拉丁字母 → 残迹扫描假阳性翻倍

**症状**：成品残迹报告里出现 `Dynamism) ##FHJIt`、`SaaS tnitTtA"SaaS KE"`、`1#FHJ QVC.`
这类"英文"，其实是对**我们自己写入的中文**的误读。

**处理（两道闸）**：
- `is_english()` 要求整串 ASCII 可打印 + 字母占比 ≥ 0.6 + **置信度 ≥ 0.5**。
  中文被误读时 Vision 置信度稳定落在 0.3。加上置信度闸，假阳性 553 → 251。
- 仍有 conf=1.0 的漏网 → 用 **62_verify_residue.py 回源核验**（见下条）。

### 6. 回源核验的裁片太小 → 核验结论不可信

**症状**：第一次核验 59 条里只找出 2 条 `real`，但其中 `SaaSpocalypse?` 明明是源图里就有的英文。

**真因**：裁片只有 38.7×8.5pt，6 倍放大后 232×51px，Vision 读不出内容 → 全部判成 noise。

**处理**：
- 外扩量随块尺寸走：`pad = max(2pt, 0.18 × 长边)`
- 四周补 24px 白边（Vision 对贴边文字识别率明显下降）
- 放大倍率提到 8 倍

改进后 59 条 → real 6 / lookup 21 / noise 32，结论才可信。

### 7. 回源核验的停用词污染

**症状**：把 `#LWMAE*0K45 The Brattle Group,` 判成 `real`，理由是与源图文本共有单词 `the`。

**处理**：交集判定要**剔除停用词**（the/and/for/with/from/that/this/are/was/has/have/not/but/all/you/our/its/out/per/see）。
`62_verify_residue.py` 里是 `STOP` 集合。

### 8. "源 OCR 未检出" 被当成真漏 → 大量假阳性

**症状**：残迹报告里 119 条 `unseen`，逐条看绝大多数是**重复的 OCR 读数**或品牌名。

**真因**：早先版本用**过滤后的候选池** `scope["in_image"]` 当源侧索引。
凡是被 `--min-h` 挡掉的块，回溯时当然找不到 → 全被扣成 `unseen`。

**处理**：源侧索引要用**原始 OCR**（`ocr_raw4.json`），不是过滤后的池子。
改掉之后 `unseen` 从 119 降到 98（v1.2 上）。

### 9. 竖排标题"看起来漏了"其实是重复读数

**症状**：核对时列出 214 条"完全没进工作单"的 h≥5pt 英文，
其中 23 条是 `Change in Net Income ($B)`、`Median Profit Margin` 这类纵轴标题。

**真相**：这些标题**已经译了**（计划里有 50 条 `rotate=90` 条目）。
列出来的那些是 OCR 对同一条标题的**第二次读数**（bbox 略不同、文本带后缀）。
判断"某处覆盖了没有"必须用 **bbox 重叠**，不能用文本相等。

## 三、排版与字体类

### 10. 单行单元被整体缩字

**症状**：`rebuild_report.json` 里 `auto-shrunk` 出现 0.926 这类数值，某几行字明显比邻居小。

**真因**：单行单元的行高有冗余（行距空白）。若文本框下方紧贴障碍物，
排版引擎判定"装不下"，就把整行缩字。

**处理**：向下补足行距空白（补的是空白，字形位置不变）：

```python
if len(u["lines"]) == 1:
    need = lh_ratio * size
    deficit = need - box.height
    if 0 < deficit <= 0.3 * size:
        box.y1 = min(box.y0 + need, page.rect.height - 2)
```

验收时 `auto-shrunk` 必须为 0。

### 11. 窄框里中文被压到 0.3 倍

**真因**：起始字号只按块高估算，没考虑中文需要的横向字数。

**处理**：`起始字号 = min(块高 × 0.78, 框宽 / 字数 × 1.25)`。

### 12. 竖排标签旋转后跑偏出框

**真因**：旋转后的插入框与 bbox 中心不重合。

**处理**：改为**逐字换行**（窄框里一字一行），位置严格沿用原 bbox。
视觉上等价于竖排，且中文逐字正立反而更易读。

### 13. 大标题"没翻译"

**真因**：标题以「透明位图 + 文字层」双份存在。译文写进了文字层，
但中文比英文短，右侧露出底下的英文位图。

**处理**：L3 —— 从背景图裁同位置像素替换标题位图。

### 14. 覆盖后英文还从旁边露出来

**真因**：中文比英文短，补丁矩形没有覆盖完整的原英文矩形。

**处理**：检查 `size_cap` 与补丁 bbox；必要时把 bbox 右边界外扩到原英文的实际右沿。

### 15. 微标签原字号直译 → 中文糊成一团

**症状**：把 2.1pt 的 `Coolant distribution unit` 直译成 2.1pt 的「冷却液分配单元」，
渲染出来是一团灰糊，比原来的英文更难读。

**真因**：中文笔画密度远高于拉丁字母，同等字号下可辨认度差一个档。

**处理**：微标签**必须放大到 ≥3.6pt** 才值得译，且放大后要用碰撞护栏（见 SKILL.md 第四节）。
不改字号就直译 = 负优化。

## 四、工程流程类

### 16. gid 段位冲突 → 静默覆盖

**症状**：补扫条目的译文把主工作单的译文覆盖了，翻出来驴唇不对马嘴。

**真因**：新工作单从 `0001` 起编号，与主工作单撞号。

**处理**：段位约定 `0001+` 主工作单 / `9001+` 补扫 / `9500+` 微标签，不复用。

### 17. 全局重建计划 → 丢掉已有条目

**症状**：往计划里加补充条目后重跑 `31_build_l2_plan.py`，原有 1,277 条变成 1,207 条。

**真因**：全局重建会改变重叠去重的结果（新增条目改变了排序与 accept 顺序）。

**处理**：**增量合并**（`32_merge_l2_plan.py`）：保留原条目，新条目按 bbox 重叠去重后追加。

### 18. 页码基准不一致

不同脚本的页码基准可能不同。本项目实测：`units.json` 是 **0 基**，`ocr_scope.json` 是 **1 基**。
每个脚本头必须注明基准，跨脚本合并前先统一。

### 19. macOS 文件系统大小写不敏感

删 `data/soxl.csv` 会连带删掉 `data/SOXL.csv`。删文件前先确认实际文件名（`ls` 看真名）。

### 20. zsh 交互式不认行尾注释

给你的命令**不要带行尾 `#` 注释**。zsh 的 `interactive_comments` 默认关闭，
会把「`#` 说明」整段当参数传进去。要写说明另起一行，或先 `setopt interactive_comments`。

### 21. bash 3.2 的变量名吞全角字符

macOS 自带 bash 3.2：`$VAR` 后面紧跟**全角字符**（如 `$LABEL）`）会被并进变量名，
报 unbound variable。一律写成 `${VAR}`。

## 五、OCR 类

### 22. zoom 太低 → 小字误识

2.2 倍渲染时 5pt 以下文字误识严重（`$OB` → `$0B`、`OpenAl` → `OpenAI`）。
**zoom 必须 ≥4**。

### 23. Vision 读不出旋转文字

整页模式下旋转 90° 的纵轴标题基本整块漏掉。解法见 `workflow.md` 的 `13_scan_vertical.py`。

### 24. OCR 框位串到邻位

小块的 OCR bbox 常常偏大，回源核验时会读到旁边那行。这类结果标记为 `lookup`，需人工看，
不要直接当成残迹。

### 25. OCR 输出坐标是**底边原点**

macOS Vision 的归一化 y 从**页面底部**起算。换算到 PDF 的顶边原点坐标：

```
y_top = page.rect.height - (y + h) * page.rect.height
```

忘了这一步，所有补丁会上下镜像 —— 而且看起来"像是没生效"，很费时间。
（`12_scan_image_text.py` 里已处理，自己写新脚本时要记得。）

## 六、补充：对齐、封面位图标题、图像流、解释器

（这一节的条目是实现 L1 对齐精判与 L3 封面换图时踩出来的，按主题归类，编号接续上文。）

### 26. 所有单行标题被当成左对齐 → 视觉中心整体左移

**症状**：全文翻完，看着"对"，但封面日期、章节小标题、图表面板标题都比原来偏左一点。

**真因**：抽取脚本对**单行单元一律写死 `align = "left"`**（只有多行才会去比较行边界）。
译文比原文短，左边缘原地不动 → 视觉中心左移。实测封面日期偏左 **20.6pt**。

**处理**：`22_fix_align.py` 精判。单行按四步兜底：
锚点（同页水平重叠的多行单元，沿用其对齐轴）→ 同行中点 → 同行继承 → 页面居中/靠右。

**两个细节**：锚点要**遍历全部候选**，只看最近的那个会漏（实测某页两个大标题靠遍历才救回来）；
页面兜底只在**本页没有多行单元**时才启用（封面这类整页设计稿）。

### 27. 多行居中块漏判 → 因为死阈值和尾随空格

**症状**：明明是居中的引文/图注，判成了左对齐。

**真因**：判据是「行坐标极差 < **固定 1.5pt**」。末行的尾随空格把 bbox 撑宽、
把中心推偏约 **1.7pt**，恰好越过 1.5 → 居中变左。
实测 p82u01 极差 1.75 / p77u01 1.86 / p84u01 1.84 / p27u10 1.55，**全部漏判**。

**处理**：两处改动——

- 容差**随字号缩放**：`tol = max(1.5, 0.15 × 字号)`。
  6pt 的窄栏里行宽差异天然只有 1~2pt，固定 2pt 会把"居中"和"左对齐"混为一谈。
- 三条轴（x0 / x1 / 中心 cx）**取极差最小的那条**，并要求"决定性"
  （最紧轴 ≤ 0.6 × 次紧轴）。**不要用固定优先级**——2 行单元里 x1 极差常恰好过关，
  固定顺序会把居中误判成右对齐；但光取"最小"也不行，某 2 行单元中心极差 0、
  而 x0 极差 1.74 更小会抢胜，所以必须加决定性判据。

**诊断口径**：全篇 `center` 数量明显少于肉眼所见 → 就是这个病。实测某 90 页稿原本 27 条，
实际应为 72 条（改判 45 条）。

**验收口径**：改判后逐条核对**渲染文字有没有超出原 bbox**。
实测 45 条全部内缩在原框内（最大偏移 −0.15pt）。

### 28. 封面大标题整块没翻 → 它是"只有位图"的美术字

**症状**：内文全翻了，封面大标题还是外文。在文字层里搜那串字，**搜不到**。

**真因**：大标题是**透明位图**（一张铬金属质感图 + 一张灰度蒙版），
压在同位置的黑色阴影层之上，**文字层里根本没有它**。
于是文字层抽取碰不到、图内文字 OCR 也读不到（它不是"图里的文字"，是美术字）。

注意与"位图 + 文字层双份"的区别：那种情况文字层能翻，只需抹掉位图（见第 13 条）。
**只有位图**的必须原位换图。

**处理**：`42_make_cover_art.py` 生成目标语言美术字 → `43_cover_title.py` 原位换图。
新图沿用**完全相同的像素尺寸与放置矩形**，只换字形像素与蒙版 —— 版面结构上不可能位移。

### 29. 按 xref 定位标题层会失手 → xref 在管线里会变

**症状**：在原始 PDF 上 `--list` 看到标题图是 xref 14，对着 L1 阶段的产物用 xref 14，
报"找不到图层"或者换错了对象。

**真因**：**xref 号不稳定**。`24_rebuild_text.py` 重写过文档，
同一张标题图到 L1 阶段就变成 xref 9 了。而且蒙版 xref 根本不在页面的图像列表里
（它只是别人的 `/SMask`，`get_image_rects()` 返回空）。

**处理**：改用**「像素尺寸 + 放置矩形」**定位 —— 这两样被管线原样保留
（实测浮点误差 < 0.02pt），是可靠的锚。`43_cover_title.py --list` 会把
尺寸和矩形打印成可直接照抄的形式。

### 30. 换图后是雪花噪点 → JPEG 字节进了 FlateDecode 流

**症状**：标题区域变成一片彩色噪点。

**真因**：保存时带 `deflate_images=True`，PyMuPDF 会把 `/DCTDecode` **改写成**
`/FlateDecode`，但流里的内容仍然是 JPEG 字节 → 解码出来是噪声。
本 skill 的默认保存参数就是 `deflate_images=True`，所以只要写 JPEG 字节就中招。

**处理**：写**解压后的原始像素**，并显式声明 `/Filter`、`/ColorSpace`、
`/BitsPerComponent`、`/DecodeParms`。

### 31. 换图后大面积全黑 → 双重压缩

**症状**：只有最上面一小条有内容，其余全黑（实测蒙版 878 行里只有 17 行有墨）。

**真因**：`Document.update_stream()` **默认 `compress=1` 自己就会压**。
再手动 `zlib.compress` 一遍就是**双重压缩**，解码时只有开头一小段能读出真数据。

**处理**：只传原始像素，压缩交给 `update_stream`。

**排查手法**：把换过的那张蒙版单独抽出来看含墨行数，一眼就能定位。

### 32. 封面金属字比原文笨重 → 中文字重照搬了拉丁字观感

**症状**：字是翻对了、位置也对，但看起来像"3D 浮雕贴纸"，比原设计重一档。

**真因**：直接拿原来最粗的字重（Black）去渲染。**汉字笔画密度远高于拉丁字母**，
同等字号下观感天然更重；再加上外描边和倒角，会进一步加粗。

**处理**：换几个字重（Regular / Medium / Bold / Black），**叠在真实封面背景上**对比再定。
对比图要先把标题区用邻近背景填掉，否则底下的原文会干扰判断。
实测某细笔画拉丁衬线标题对应 Noto Serif SC 的 **Medium**。

另外两条美术字质感经验：
- **亮度不要从原图取**——原图逐行平均是「暗斑 + 亮边」的混合，填出来只能是灰调（像拉丝铝）。
  改为**只取色温**（高光像素均值归一化），亮度用程序化的"亮-暗-亮"纵向节奏。
- **倒角必须窄**（字高 1.3% 量级）。宽倒角会让笔画整体渐变、看着发胖。

### 33. `Rect.get_area()` 在某些 PyMuPDF 版本里没有

**症状**：`AttributeError: 'Rect' object has no attribute 'get_area'`，脚本直接崩。

**真因**：实测 PyMuPDF **1.26.5 没有**这个方法，**1.28.2 有**。
同一台机器上如果既有系统 python 又有 venv，很容易踩——两边版本不同。

**处理**：不要用 `get_area()`，自己算：`abs(r.width * r.height)`。
本 skill 的脚本已全部改成自算。

### 34. 用错解释器 → 装了库的那个才是对的

**症状**：`ModuleNotFoundError`，或者某些方法不存在（见上条）。

**真因**：机器上常有多个 python（系统 / Homebrew / venv），
文档里写"系统 python 就够"是**不可靠的**——实测某个项目里只有 venv 那个装了正确的
PyMuPDF 版本，系统那个版本偏旧。

**处理**：开工前先确认：
```bash
python3 -c "import pymupdf, numpy, PIL; print(pymupdf.__version__, pymupdf.__file__)"
```
把实际用的解释器**绝对路径**写进项目规则文件，别写 `python3`。

### 35. 打包进 skill 后残留项目绝对路径 / 项目文件名

**症状**：skill 在别的项目里跑不起来——报"找不到文件"，或者去操作上一个项目的产物。

**真因**：项目脚本里散落着本机绝对路径和各种变量名写死的路径
（`BASE = "~/项目/xxx"`、`SRC = "~/项目/xxx/xxx.pdf"`、`WORK = "~/项目/xxx/work"`、
`FONTS = "..."`），以及把项目产物名当 argparse 默认值
（`--pdf default="output/某某报告_v1.1.pdf"`）。复制到 skill 时只改了 `BASE` 那一行。

**处理**：打包时做**统一的通用化改写**，并且**打包后自检**：

1. 绝对路径 → `BASE / "<相对>"`；
2. 项目文件名 → 占位名（`input.pdf` / `product.pdf`）；
3. `BASE` 的各种写法统一成 `os.environ.get("XTRANS_BASE", Path.cwd())`；
4. **引用了 `BASE` 却没定义** → 补一行定义（有些脚本原本只写了绝对路径的 `SRC`/`WORK`，压根没有 BASE）；
5. 品牌装饰字正则 → 改成可用 `XTRANS_DECOR` 环境变量覆盖；
6. 自检三条：**无残留绝对路径**、**无残留项目文件名**、**用到 BASE 就必须有定义**。

⚠️ 第 4 条最容易漏：只把 `SRC = "/abs/xxx.pdf"` 换成 `BASE / "input.pdf"`，
而不补 `BASE` 的定义，脚本一跑就是 `NameError`。
（补充定义的插入位置要注意：要插在文件**开头那段** import 之后，
不能取"文件里最后一个 import"——否则会插到文件中部，很丑。）

## 七、成果检验类（T0–T3 建立过程中踩出来的）

（这一节是搭 `63–69` 检验框架时，在真实成品上逐条校准出来的。凡是"报出红项"的，
都先假设是**工具错了**，用渲染回看、独立复现把它证伪或证实，再决定改工具还是改成品。）

### 36. ★ 文字层抽取出生僻字 / 希腊字母（字形码越过 ToUnicode 覆盖范围）

**症状**：成品能看、能打印，OCR 渲染出来的像素也读得出真字符，但**文字层里抽取出来是别的东西**。实测两例：
- `N=148-160` 抽出来是 `N=睹睼瞀-睹睾睸`（数字 → 生僻汉字）
- `Snowflake` 抽出来是 `SnowΚake`（`fl` 连字 → 希腊字母 Κ）

因为 `a16z` 里的 `16` 也走这条路径，**发行方自己的品牌名在成品里是 `a睹睾z`**。只有复制、搜索、文本抽取、无障碍读屏是错的。

**根因（用 `page.get_texttrace()` 取证确认）**：`insert_htmlbox` 有时把字符的**码**写成该字体**原始字形的 id**（几千量级），而不是它登记进 ToUnicode 的那个码。那些码不在 ToUnicode 里，**抽取端就回退成 `chr(code)`**：

| 场景 | 写入的码 | ToUnicode 里 | 抽取结果 |
|---|---|---|---|
| 正常数字 `2` | `0x0013` | 有 → U+0032 | `2` ✅ |
| CJK 字体里的数字 `0` | `0x7778` | **无** | `chr(0x7778)` = 睸 ❌ |
| Roboto Italic 的 `fl` 连字 | `0x039A` | **无** | `chr(0x039A)` = Κ ❌ |

**一句话规律**：**写入的码 > 该字体 ToUnicode 的覆盖上限 → 报 `chr(code)`。**
Noto Serif SC 的 CMap 覆盖 30,424 个码（`0x7778`=30584 刚好越界）；Roboto Serif Italic 只覆盖 919 个（`fl` 连字的字形 id 922 刚好越界）。这就解释了为什么**数字落在低位就没事、连字落在高位就出事**——同一个原因。

**"码位连续"是这类损坏的签名**：数字 0–9 的原始字形 id 恰好是 `0x7778`–`0x7781`，`chr()` 出来就是 `睸睹睺睻睼睽睾睿瞀瞁` 一串连号。字符集核验报出连续码位，基本可以一眼确认。

**影响范围**：**L2/L2b 图内补丁最密集，但 L1 文字层同样会中**（`SnowΚake` 那例就是 L1 的 units #173）。不能只盯覆盖层。

**不是 `subset_fonts()` 或 save 参数造成的**：逐个隔离测过（`subset_fonts` 加/不加、`clean` 开/关、`garbage`、`deflate*`、全默认 `save()`）——**结果全部一样**。是 `insert_htmlbox` 排字那一刻就写进内容流了。

**取证手法**：`page.get_texttrace()` 直接给出每个字符的 (unicode, glyph_id)。一眼就能看出「同一串里正常的数字是 17/19，坏掉的是 30584/30585」。

**改法实测结果**：

| 改法 | 结果 |
|---|---|
| 单一 CJK 字体（默认） | ❌ 数字全坏 |
| 加 / 去掉 `subset_fonts()` | ❌ 无变化 |
| CSS 字体列表 `font-family: sc, lat` | ❌ 无效——HarfBuzz 不会在同一个 run 内逐字形回退 |
| **把每个 ASCII 数字包进拉丁字体的 `<span>`** | ✅ 修复（拉丁字体里数字落在低位码） |
| **拉丁 span 上关连字（`font-variant-ligatures:none` / `font-variant:no-common-ligatures`）** | ❌ **MuPDF 的 HTML 引擎无视这两种 CSS**，连字照做（2026-10-06 隔离实测：抽取文本与不加时逐字节相同） |
| **在每个 `f` 之后切成相邻 span**（f 收段尾 → 跨段不成连字） | ✅ 唯一有效的连字抑制，且不引入额外字符；`Snowflake` 抽取干净（`oﬃce` 的 ffi 同步消失） |

```python
# 写补丁文本前，把数字逐个套上拉丁字体
html = "".join(f'<span style="font-family:lat">{c}</span>' if c.isdigit() else c
               for c in text)
css = f'@font-face {{ font-family:"sc";  src:url("{CJK_FONT}"); }}' \
      f'@font-face {{ font-family:"lat"; src:url("{LATIN_FONT}"); }}'
```

**检测**：`64_audit_text.py` 的字符集核验（第 ⑤ 项）会直接把"凭空出现的字符"列出来。
**这个坑靠肉眼和对照图都发现不了**——必须靠文字层抽取，这是 T1 存在的理由。

**连字 ≠ 损坏**：`⸺`(U+2E3A)、`ﬃ`(U+FB03) 是字体把相邻字符合并成字形，**ToUnicode 里有条目**、只是指向连字码位，语义等价、观感一致，仅按原串搜索失效 → 归 `benign`。
判定口径要落在「**该字体 ToUnicode 的覆盖上限**」，而不是「看起来像不像乱码」。

### 37. 连字被当成字符损坏 → 假红项

**症状**：字符集核验报出 `⸺`（U+2E3A）和 `ﬃ`（U+FB03）"凭空出现"。

**真因**：这是**字体把相邻字符合并成一个字形**（`——` → `⸺`、`ffi` → `ﬃ`），
语义等价、观感一致，只是按原串搜索会失效。它们不在"我们打算写的字符"集合里，所以被当成异常。

**与第 36 条的区别**（这是关键）：连字在 ToUnicode 里**是有条目的**，只是指向连字码位；
而 36 条那种损坏是**表里根本没条目、抽取端 `chr(code)` 兜底**。前者良性、后者必须修。

**处理**：加 `BENIGN_CHARS = U+FB00–U+FB06 连字 + U+2E3A/U+2E3B 破折号连字`，
归为 `benign`，**只警告不报红**。更稳的判据是查「该字体 ToUnicode 的覆盖上限」——
越界的才是损坏。

### 38. 数字校验满屏误报（407 → 4）

**症状**：第一版数字守恒校验报出 407 条"数字丢失"。

**真因（四个叠加）**：

- 正则把形近字 `o/O/l/I/S/s` 当数字，`falls,` 里的 `lls` 被译成 `115`，`S1O0`、`10s`、`1990s` 也造出幽灵数字；
- 把**货币量级换算**（`$97.4B` → `974 亿`）当成丢失；
- 把**日期重排**（`Aug 11, 2026` → `2026 年 8 月 11 日`、轴标 `Jan 12` → `1/12`）当成丢失；
- 源侧 OCR 垃圾块（带 `?` 或超长数字串）混进来。

**处理**：token 加四条约束（必须以真数字开头 / 左侧不紧邻字母数字 /
形近字只在数字串内部 / 剥掉尾部复数 `s`），再把不匹配项分四档
`check`/`unit`/`date`/`noise`，**只有 `check` 是红项**。407 → 4。

### 39. 专有名词核验报出 407 条，几乎全是噪声

**症状**：①/② 项一开始报出 407 条候选。

**真因（三类）**：

- 中文习惯就是直接用缩写的（`US`、`VC`、`EV`、`Q2`），被当成"没统一"；
- 2–3 字母的代码、1 字母 + 1 数字的期间标记（`Q1`/`H2`）本就没有"译法"可言；
- 有些条目的 `tgt` 是**空串**（该块没被覆盖），空 `tgt` 会让"保留率"分母虚高，
  直接报成红项。

**处理**：裸代码要求 ≥4 字符、排除 1 字母 + 1 数字的期间标记、`min_occ` 提到 3–4、
**丢掉 `tgt` 为空的条目**。407 → 1 → 0。

### 40. `a16z.com` 保留率 7% 的假红项 → 是字符损坏的连锁误报

**症状**：术语核验说 `a16z.com` 的"保留率只有 7%/25%"，像是被漏译了。

**真相**：成品里实际是 `a睹睾z.com`（第 36 条）。**坏掉的 `tgt` 让"这个词还在不在"
这个判断本身失效了。**

**处理**：让字符集核验（⑤）充当**输入过滤器** —— `tgt` 含坏字符的条目
先剔出 ①/②/③，只由 ⑤ 统一报一次。这是"检查项之间有依赖"的典型：
**完整性检查必须排在一致性检查之前**。

### 41. 报"某处年份被改了"其实没改（源侧 OCR 误读）

**症状**：p37 报出"原文年份 2020，译文写成 2026"。

**真相**：**源图**上是 `Aug 11, 2026`，是**源侧 OCR 把它读成了 2020**。
译文是对的，错的是喂给校验器的源文本。

**处理**：这类**只能人工判**——渲染源图回看即可确认。它不是工具 bug，
而是"上游数据错了"这一类，必须在报告的诚实清单里写明，不能靠改判据消除。

### 42. 报"A 处的译文是 B 段文字"（几何配对错位）

**症状**：p48 报出某条译文与源文完全对不上。

**真因**：源 OCR 的切块（`Ariane 62`）与覆盖计划里的切块（`$8,495/kg`）**分段方式不同**，
按几何位置配对时串了块。

**处理**：同样只能人工判。**配对表里所有"完全对不上"的项，先怀疑切块不一致，
不要直接当成漏译。**

### 43. 分层抽检所有页归成一类

**症状**：`chapter 35 / dense 53 / chart 1` —— 90 页几乎全被塞进"密集页"。

**真因**：分层阈值写死了绝对值（`l2 >= 40`、`chars <= 200`）。
而这个项目**每页都有整页图片**，图片面积 `img_area` 全部 >1.4，所有页在某一维上完全相同。

**处理**：**阈值一律取本项目自身的分位数**（`quant(vals, p)`）。
不同项目的页数、图片密度、正文字号差得很远，写死阈值换个项目必然塌掉。

### 44. 回译把 9/14 条好翻译报成漂移

**症状**：第一版回译核验把 14 条里的 9 条标成 `drift`，逐条看全是对的。

**真因**：拿**措辞相近度**（token 重叠 Jaccard）当判定阈值。
但**好翻译**的 Jaccard 也只有 **28%–46%**——中文常做近义词替换
（`great leap forward` ↔ `huge jump`、`showing up` ↔ `reflected`）。
这是翻译的常态，不是缺陷。

**处理**：把 Jaccard **降为排序信号**，只把两条提为硬判据：
**数字不符**、**长度比失衡**（`0.45–2.2` 之外）。9 条 drift → 0 flag / 3 watch。

**定位**：回译是**排序工具，不是判定工具** —— 它负责把"最值得看的几条"排到前面，
让人的 10% 抽检时间花在刀刃上。拿它下结论一定翻车。

### 45. 否定词检测大面积漏判

**症状**：源文 `aren’t`、`non-normal` 判不出否定极性，全漏。

**真因（两处）**：报告用的是**弯引号**（`aren’t` 用的是 U+2019，不是 `'`），
只认直引号会全漏；且 `non-` 与 `not-` 是**同义的两种构词**。

**处理**：正则同时认 `'` 和 `’`，同时认 `non`。**并且把这一项从硬判据降为提示**——
`already`、`unmatched` 并不是否定，硬判会误报。

### 46. 汇总报告里的 Markdown 表格被打断

**症状**：`QC_REPORT.md` 渲染出来表格错位、串行。

**真因**：源文/译文的文本里**带换行是常态**，直接塞进 Markdown 表格单元格会把整张表打断。
脏数据里还有 `|`（表格分隔符本身）。

**处理**：所有单元格过一遍净化 —— 折叠空白 + 转义 `|`：

```python
def cell(v):
    """表格单元格净化：折叠换行与管道符。源/译文本里带换行是常态，
    直接塞进 Markdown 表格会把整张表打断（实测过）。"""
    return re.sub(r"\s+", " ", str(v)).replace("|", "\\|").strip() or "—"
```

### 47. T0 把目录页的页码当成"章节标题缺失"

**症状**：结构断言报"目录页标题不含中文"。

**真因**：目录页上的 `01`–`08` 是 **14pt 的"标题"**（字号达到标题阈值），
但它们没有任何可译内容，也没有对应中文标题。

**处理**：纯数字"标题"用 `NUMERIC` 正则 + `passthrough` 标记排除。
**标题完整性判据不要只按字号筛，还要排除"不是语言"的东西。**

### 48. 成品里多份字体共用同一张 ToUnicode

**症状**：核验时发现 16 个字体对象只对应 5–7 份 ToUnicode CMap。
根因排查时一度以为这就是第 36 条的成因。

**实测**：源 PDF 是 **9 个字体 / 9 份 CMap**（一一对应）；
经管线后变成 11 字体 / 5 份 → 16 字体 / 7 份。被合并的典型：

```
ToUnicode 867  ←  SRGOWL+Noto Serif SC Regular
                  NMGZVC+Noto Serif SC Bold
                  XUBYXM+Noto Serif SC Black
                  KYBWPN+Noto Serif SC Medium
                  TRPRNP+ / LMYUKC+ Noto Serif SC Regular
ToUnicode 861  ←  JRYHTP+Roboto Serif 20pt
                  JLNQLC+Roboto Serif 20pt Bold
                  ERDRVG+Roboto Serif 20pt Italic
```

**结论：这不是第 36 条的成因。** 单字体、单页的最小复现同样会坏（第 36 条已证实与
`subset_fonts` / save 参数无关）。而在本例里，这些共用 CMap 的覆盖范围恰好够用，
**未观测到由此产生的错误抽取**。

**但要记着它**：它的存在说明"每份 CMap 覆盖哪些码"不能靠猜。核验时应当**按字体逐份解析
CMap、拿到覆盖上限**，再判断某个字形码是否会触发 `chr(code)` 回退——这比"看字符像不像乱码"可靠。

**排查手法**：

```python
# 逐页收集字体 → ToUnicode，按 CMap 分组看谁被共用
obj = doc.xref_object(font_xref, compressed=True)
tu = re.search(r"/ToUnicode\s+(\d+)", obj)
cm = doc.xref_stream(int(tu.group(1))).decode("latin-1")   # 按 beginbfrange/bfchar 分块解析
```

⚠️ 解析 CMap 时**必须按 `beginbfrange`/`beginbfchar` 分块**再匹配三元组。
全局一把梭的正则会把「上一行的 `<码> <Unicode>`」和「下一行的 `<码>`」串成假三元组，
凭空造出大量互相矛盾的重叠区间（踩过，白排查一轮）。

## 八、绝对红线：原文件不可改动

红线只有一句：**整个过程不可以损坏原文件，不要对原文件进行任何的改动。**

但"我觉得我没动它"和"它确实没被动过"是两件事。所以把危害面精确测了一遍
（PyMuPDF 1.28.2，每个写法都真跑过，不是推测）：

### 49. ★ 只有 `saveIncr()` 会静默改写原文件

| 写法 | 实测结果 |
|---|---|
| `doc.save(源路径)` | 被 PyMuPDF 自己拒绝：`ValueError: save to original must be incremental` |
| `doc.save(源路径, incremental=True)` | 被拒：`FzErrorArgument: Can't do incremental writes when changing encryption` |
| **`doc.saveIncr()`** | **★ 静默就地改写**：3,603,6029 → 3,603,7211 字节，哈希变了 |
| `chmod 444` 后再 `saveIncr()` | 被系统拒绝：`Permission denied` |
| `chmod 444` + `uchg` 后再 `saveIncr()` | 被拒绝：`Operation not permitted` |
| `chmod 444` + `uchg` 后 `mv` / `rm` | 都是 `EPERM`——连改名和删除也一并挡住 |
| 加锁状态下正常读取 | **完全不受影响**（页数、抽文字都对，PyMuPDF 本来就是只读打开） |

**结论**：最蠢的写法库已经替我们拦住了，**要防的只有 `saveIncr()`**。它的阴险之处在于
"只追加几百字节、文件结构仍合法、能正常打开、界面看不出任何异常"——**除了哈希没有别的办法发现**。

**处理分三层**：

1. **代码层**：任何 `save*` 的目标路径必须是显式参数，永远不指向源路径。不要依赖库来兜底——
   换个库、换个版本，那层保护就没了。
2. **流程层**：`67_source_guard.py`——开工 `--record` 记 SHA-256 基线，收工 `--check` 复核，
   不一致就退出码 1 并停下来。（部署到具体项目时它排在流程最前，项目侧编号习惯写作 00，
   打包进技能后统一为 67。）
3. **物理层**：`--seal` = `chmod 444` + macOS `uchg`。实测 `chmod 444` **只挡得住"改内容"**，
   改名/移动/删除照样能做；叠一道 `uchg` 之后 `mv`/`rm` 也变成 `EPERM`，才配得上"不要对原文件
   进行**任何**的改动"这句话。

**两个容易做错的细节：**

- **解锁顺序不能反**：`uchg` 在位时 `os.chmod` 会 `EPERM`，所以 seal / unseal 都必须
  "先 `set_uchg(p, False)` 再 `chmod`"。这个顺序顺带让 `--seal` 变成幂等的（重复执行不报错）。
  另外只动 `UF_IMMUTABLE` 这一个位，**不要 `chflags(p, 0)` 整体清零**——那会顺手把用户
  自己设的 hidden 之类的标志抹掉。
- **基线发现不一致时，默认必须拒绝重建**。如果"顺手重建基线"是默认行为，这条红线等于没有——
  误写会被自动洗白。必须显式 `--force`，而且要把"基线被重建"打印出来留痕。

### 50. 复核把"时间戳变了"当成"文件被改了" → 满地假警报

**症状**：加了 mtime 比对之后，什么都没做也报 FAIL。

**真因**：备份、同步盘、iCloud、`touch` 都会碰修改时间；`chmod` 也会被算进去，
而 `--seal` 本来就要 `chmod`——于是**每次加锁之后复核必然冒一条假警告**。

**处理**：**判定只认内容**。`sha256` 或 `size` 变了才是 FAIL；`mtime` 变化降为 WARN
（提示"有人碰过这个文件，去问一句为什么"）；权限位只写进说明列，不参与判定。

为什么放宽时间戳不会漏掉真问题：`saveIncr()` 那类误写**一定会改到内容**。
反过来，假警报一多，红线就没人看了——**报警的准确率本身就是这套机制能不能活下去的前提**。
